# 06 — Static serving + Docker Compose wiring

Status: resolved
Blocked by: server/01, editor-app/01

Serve the built `apps/web` static bundle (Caddy: static files + reverse proxy `/api` and admin routes to the api container). `/export` route must be served from the same origin the worker hits (loopback to Caddy). Compose services: `caddy`, `api`. TLS via Caddy + Cloudflare DNS (docs in launch/04). Volumes: sqlite db, exports-history dir.

**Accepts**: `docker compose up` serves the app with working API + same-origin `/export` reachable by the worker.

- **Caddyfile** (repo root): one `(serve)` snippet, imported by two site blocks — `{$SITE_ADDRESS::80}` (public origin; `:80` locally, a domain gets Caddy's automatic TLS in launch/04) and `http://caddy` (the worker's loopback origin: plain HTTP on the compose network, independent of the public site's TLS, so `EXPORT_ORIGIN=http://caddy` works with or without a domain). The snippet: `encode zstd gzip`; `/assets/*` immutable caching (content-hashed filenames); `X-Robots-Tag: noindex` on `/export*` (spec: security posture); `@backend path /api /api/* /healthz` → `reverse_proxy` (admin routes ride `/api/admin`, gated server-side by `is_admin`); everything else `try_files {path} /index.html` + `file_server` for SPA deep links. API proxying lives in its own `handle` block *before* the SPA `handle` so `try_files` can never rewrite an API path.
- **apps/web/Dockerfile**: multi-stage like the server's — pnpm workspace install, builds `@perfectmarkd/core` then `@perfectmarkd/web` (the bundle imports core's built `dist/`), bakes `apps/web/dist` into `caddy:2` at `/srv` with the Caddyfile at `/etc/caddy/Caddyfile`. Build context is the repo root (workspace lockfile).
- **docker-compose.yml**: services `caddy` + `api` (existing server Dockerfile, unchanged shape); named volumes `api-data` (SQLite db + encrypted history, both under `/data` per the image's `VOLUME`) and `caddy-data`/`caddy-config` (TLS certs). `SESSION_SECRET`/`HISTORY_ENCRYPTION_KEY` are `:?`-required (fail at parse time, not boot), `ADMIN_EMAIL` optional, `EXPORT_ORIGIN=http://caddy` hardcoded (ADR-0003: the worker renders the same origin browsers use). Compose-level healthcheck on `api` mirrors the Dockerfile's so `depends_on: service_healthy` works on every runtime (podman's compat API hides image-level healthchecks). Port knobs `CADDY_HTTP_PORT`/`CADDY_HTTPS_PORT` for hosts that can't bind low ports (rootless daemons).
- **Fixed a pre-existing api-image regression**: server/03 made the export pipeline import `@perfectmarkd/core` at *runtime* (`injectPDFOutline`, `DEFAULT_SETTINGS`, `validate`), but `apps/server/Dockerfile` never built core — `tsc` failed to resolve it (its entry points resolve to `dist/`) and the `pnpm deploy` tree would have shipped core without `dist/`. Both stages now build core first (build stage before `tsc`, deps stage before `deploy`). Not caught earlier because CI has no Docker.
- **Verified** (`caddy validate` + `docker compose config` + a real `docker compose up` under rootless podman): `/` and `/pricing` serve the SPA (200), `/export` serves index.html with `X-Robots-Tag: noindex`, `/healthz` and registration round-trip through the Caddy proxy (user survives an api restart on the volume), hashed assets get immutable caching, and from *inside* the api container `fetch('http://caddy/export')` returns the SPA — the acceptance's same-origin reachability, verified from the worker's vantage point. 902 workspace tests green; typecheck + lint clean.
- **Out of scope, deliberate**: Chromium is not baked into the api image — exports fail per-job until launch/04 adds `npx playwright install --with-deps chromium`; the API boots fine without it (launch is lazy). Domain/DNS/TLS rollout is launch/04's ticket (`SITE_ADDRESS` knob is the only thing it needs to set).

**Code review** (commit `bf84068` + fold):

- *Spec axis*: the TLS story is only partial for Cloudflare-proxied setups — HTTP-01 works as-is with proxy off, but origin certs / DNS-01 need a `tls` block in the Caddyfile, so that nuance is now written into launch/04's ticket (with the Chromium reminder); `depends_on: service_healthy` kept deliberately — a bad secret should fail `compose up` loudly, not bring up a half-working stack (the repo's fail-loud boot posture); README + the `API_UPSTREAM` knob are mild creep but serve self-hosters, kept.
- *Standards axis*: README no longer presents the stack as a complete deployment (Server Export needs launch/04's Chromium, now linked); EXPORT_ORIGIN comments corrected to say "loopback origin" (the Caddyfile already had it right — the same-app-different-origin nuance matters); accepted duplications, each documented in place: compose-level healthcheck mirrors the Dockerfile's (podman's compat API hides image-level ones), and the pnpm-workspace build scaffolding repeats across Dockerfile stages (Docker reality; the `deps` stage rebuild of core is seconds).
