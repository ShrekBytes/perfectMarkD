# 07: Long Documents — the ladder

**What to build:** A user with a Document far too large for one request gets a working path instead of a wall. Over the send cap, the action still runs on the part they chose, with the popup saying that only the target in full and an outline of the rest was sent. Over the write cap, a whole-Document intent becomes an **AI Plan**: one cheap action against the outline proposes what would change, section by section; the user sees how many AI Actions it will cost and how many they have left; each approved step then arrives as its own proposal, one section at a time, staying consistent because the plan travels with every step. Stopping early keeps what was already accepted. A Document with one enormous unstructured section is offered a paragraph range around the cursor instead. Something that genuinely cannot be worked on is refused with its size and the alternative stated — never truncated in silence.

**Spec:** `.scratch/ai-transforms/spec.md` (the scope ladder, the AI Plan, and the refusal paths).

**Blocked by:** 05 (the request path, the popup, the review dialog, and the primitives it wires up).

**Status:** ready-for-human

- [x] The size decision is one ladder over the Document, the target, and the configured budgets: everything fits; target fits with a digest of the rest; target past the write cap; nothing fits. The client and the server reach the same decision from the same shared code, and the server never trusts the client's numbers.
- [x] When only part of the Document is sent, the popup says so in plain words — the target in full plus an outline of the remaining sections — and the digest is built locally from the section structure with no model call.
- [x] A whole-Document intent past the write cap offers an AI Plan instead of running: the plan is produced from the outline alone, is shown for approval, and states the number of AI Actions it needs against the allowance remaining.
- [x] Running a plan produces one proposal per step, each accepted or rejected on its own, carrying the plan as a shared brief so the tone and terminology stay consistent across sections; stopping a run or running out of allowance keeps the steps already accepted and says what remains.
- [x] A target that cannot be worked on even scoped — one oversized section with no structure — offers a paragraph range around the cursor, and a request that still cannot fit is refused with its size, the configured cap, and the path forward.
- [x] Nothing in this path truncates silently, applies partially, or spends an AI Action on a step that produced no proposal; a plan is never started without the user approving it.
- [x] Tests: unit tests for each tier boundary and the digest's shape; a component test for the plan's approval surface and its action count; route tests for a plan request and a step request against a fake provider; and a manual real-browser check of a large Document's path through the popup.

## Comments

- Implemented (ai-transforms/07). The ladder is one pure decision in `packages/core/src/ai.ts` — `decideAiLadder` over the Document, the target, and `AiBudgets` — with `checkAiSendSize` as the single size check the server re-runs on every request. The server never sees the Document, so it re-derives what it can from the payload it received (the shared estimator and the same caps) rather than trusting the client's arithmetic; the route comments say so where it matters.
- The four rungs: **tier 0** everything fits (a selection takes the rest of the Document with it, so the result matches the Document it belongs to); **tier 1** the target in full plus a locally built outline digest of the sections it does not touch; **tier 2** a whole-Document intent past the caps becomes an AI Plan; **tier 3** refused with the size, the cap it ran into, and the paragraph around the caret offered. Nothing truncates: every rung either sends something whole or refuses. A section that is itself past the caps is refused on its own terms — a plan step is measured against its own section, not the Document around it.
- The write cap is derived in the shared module (`aiWriteCapTokens`: half the output budget in estimated tokens) rather than configured, so a single number cannot contradict itself. The account block now also reports `maxOutputTokens` and `contextWindow`, which is what lets the client run the same decision the server will.
- **The AI Plan** is one cheap action against the outline digest: `mode: 'plan'` on the markdown route sends the instruction, the digest, and the section labels and nothing else. The reply is parsed by the shared `parseAiPlan` against those labels, so a plan naming a section nobody has is refused whole (and costs nothing) rather than offered with holes in it. The approval dialog states the steps, the AI Actions they cost, and what the allowance has left; approving starts the run. Each approved step then runs as its own action against its own section with the plan as its shared brief, and each result is its own proposal in the review dialog. Stopping early, running out of allowance, a section that has moved, or a section that is too large all stop the run with what was applied and what remains.
- **The paragraph range** is `resolveParagraphRange` in the shared module: the run of non-blank lines the caret sits in. It is offered for a Document too large with no headings or Page Breaks to plan against, and the popup then shows it as the target with the rest of the Document as context.
- Three defects in 05 were found by this work and fixed, each of which the tests now pin:
  - **The popup's target was resolved once, at open, and the request re-resolved it at submit.** A scope narrowed to a paragraph or a selection was silently replaced by the whole Document on submit. The selection now reaches the popup through a new `onSelectionChange` on the editor extension (so the readout, the ladder, and the request all follow the editor), and `submit` sends the scope the popup is showing.
  - **The staleness check double-sliced.** `isProposalStale` slices the target's range out of the text it is given, and the controller was passing a pre-sliced range — so every proposal whose target does not start at offset 0 read as "the text this proposal targets has changed" and could never be accepted. Only whole-Document targets were reachable before, which is why nothing caught it.
  - **Heading-less sections had one label between them.** A Document split only by Page Breaks named every section `(no heading)`, so a plan's steps all resolved to the first one. `sectionLabels` now numbers them (`(no heading 1)`, `(no heading 2)`) when there is more than one, and `findPlanStepSection` resolves a step by heading first (headings survive a run's edits) and by the plan's own index for the bare ones.
- Also: the plan brief counts toward the model's window but not toward the send cap. The brief is overhead the user did not choose — a long plan would otherwise make its own steps unrunnable — and each step's section is still capped on its own.
- Verified: `pnpm vitest run packages/core/src/ai.test.ts apps/server/src/ai apps/web/src/ai` (255 tests: every tier boundary, the digest's shape, the paragraph range, the plan parser's refusals, the popup's four states, the approval surface and its cost line, the run's summary, and the route's plan and step requests against the fake provider), the full `pnpm test` (117 files, 1,506 tests), `pnpm typecheck`, `pnpm lint`, and `pnpm build`.
- Verified in a real browser: `apps/web/e2e/ai-long-document.spec.ts` (4 tests, passing) drives a Document whose budgets make a few hundred characters large: the whole-Document target offers the plan; selecting a passage makes it the target and the popup states that only part of the Document is sent; approving a plan and running it produces three proposals in turn, each accepted into the Document; stopping after the first keeps it and says two steps remain; and a Document with no headings is refused with the paragraph offered, which then runs. The rest of the browser suite passes (61 tests) except `shell-compact.spec.ts`'s "crosses to the three-pane row exactly at the panes' minimum width", which fails identically on a clean checkout with 24px of shell overflow and is not caused by this work.

- A two-axis review (standards + spec) then found six more, all fixed:
  - The window refusal stated neither size nor cap, while every other refusal names both. It now says how many tokens of text and of reply were measured against the window.
  - The client's own check for a plan step left the brief out while the server's included it, so a step the client green-lit could be refused by the server — breaking the "same decision from the same shared code" claim. `AiPlanBrief` and `planBriefText` moved into the shared module, and the client now measures the same text the server will.
  - Tier 1 told the user an outline of "the other 0 sections" was sent when a selection sits in a Document whose only section holds everything; the copy now says the selection is sent alone.
  - The budgets mapping and the plan's types were declared twice, once per side; both now come from the shared module, and the step pluralizer and the `(no heading)` label are single declarations.
  - `planCost` said "the run will stop" — CONTEXT.md's AI Plan entry lists "run" as vocabulary to avoid. The copy says "the plan will stop when the allowance runs out".
  - The ladder's three informational lines repeated their wrapper element three times; one `LadderNote` renders them.
- Review findings deliberately not taken: the plan's checkbox still uses `AiReviewDialog`'s `h-3.5 w-3.5 accent-accent` rather than DESIGN.md's touch-target floor (inherited from the review surface, and changing one without the other would leave the two surfaces inconsistent); a plan step that turns out to be too large stops the plan with the size and the smaller-range path stated rather than offering a paragraph range, because the popup — the only place that offer lives — is closed while a plan is working; and "outline" is used for the section digest as the spec and this ticket use it, even though CONTEXT.md reserves *Outline* for the PDF bookmark tree.

- Closing the run's own paths in the browser found one more defect, and one that was only claimed:
  - **A spent allowance blocked Accept.** `acceptDisabledReason` carried "No AI Actions left this period", so a proposal the user had already been charged for could not be applied — the Document stayed unchanged after an Action was counted. The reason belongs to Retry alone, where a resubmission really is a fresh Action; it is now only on `retryBlocked`, and `AiReviewDialog`'s test pins that Accept stays available while Retry and Edit prompt are blocked. The new browser run proves it: the allowance runs out while the last proposal is on screen, that proposal is accepted, and the plan then stops with "1 of 3 steps applied; 2 steps remain".
  - **The run's decisions had no test.** `apps/web/e2e/ai-long-document.spec.ts` now also covers rejecting a step and carrying on with the next (three steps, one accepted, two rejected, only the accepted one in the Document), the allowance already gone before the first step (the approval surface states it, and the plan stops with 0 applied and 3 remaining), and exhaustion between two steps (above). Both were checked against a deliberately reverted fix first, so neither passes for the wrong reason.
