# 02: The Docs page and the styling reference

**What to build:** A user can visit the Docs page, and the Stylesheet tab's footer line links to the styling reference it contains: the CSS variables and class names a Custom Stylesheet may rely on, what is explicitly internal, and the statement that page size, margins, and header/footer bands are Inspector settings rather than CSS. The reference cannot describe something the engine no longer emits.

**Spec:** `.scratch/ai-transforms/spec.md` (the styling-reference decisions and the drift test).

**Blocked by:** 01 (the reference documents what 01 introduces, and the drift test asserts those names exist in the engine's output).

**Status:** ready-for-human

- [x] The Docs page exists at its route with an in-page section nav generated from its headings, rendered from the single markdown source through the engine's markdown renderer, reachable from the existing Docs entry points.
- [x] The reference section documents the `.mpdf-doc`-scoped CSS variables and the content selectors a user is likely to need, marks everything else as internal, and states that page geometry, paper size, paper background, and header/footer bands belong to the Inspector, with `@page` named as ignored.
- [x] A test in the engine package builds the CSS with every settings branch enabled and fails if any documented variable or selector is absent from the output; documenting fewer names than the engine emits passes, inventing one fails.
- [x] The Stylesheet tab links to the reference from its footer line, and the link works from the editor without losing the open Document.
- [x] A visitor can read the section on a narrow screen in one column, and heading anchors work for keyboard and screen-reader users.

## Comments

- Implemented (ai-transforms/02). Engine: `buildDocCSS` now mirrors the settings-derived values as `.mpdf-doc`-scoped custom properties (`--mpdf-font`, `--mpdf-font-size`, `--mpdf-line-height`, `--mpdf-paragraph-spacing`, the body/heading/bold colors, `--mpdf-accent`, code background/font, blockquote background, table-header background — the spec's list exactly). The generated rules are unchanged (they keep their direct values; the variables are a read contract — redefining one does nothing), so no rendered structure moved: the golden suite and the export-HTML snapshot picked up only the added declarations. The new `styling-reference.ts` owns the contract as data (`STYLING_REFERENCE_VARIABLES` / `STYLING_REFERENCE_SELECTORS`) and generates the reference section's markdown (`buildStylingReferenceMarkdown`), plus the heading/anchor constants the tab's link uses.
- The drift test (`styling-reference.test.ts`) builds the CSS with every branch on (both heading decorations, centering, striped tables, ligatures, RTL, the Custom Stylesheet layer) and asserts every documented variable appears as a definition on `.mpdf-doc` and every documented selector appears word-bounded — documenting fewer names passes, inventing one fails. It also pins the variables' settings-derived values and the anchor chain end-to-end (`STYLING_REFERENCE_HEADING` → the renderer's slug → `STYLING_REFERENCE_ANCHOR`).
- Web: `apps/web/src/docs/` — the single `docs.md` source (getting started, Page Breaks, Presets and the Inspector tabs, math/diagrams/tables with live examples, the font catalog, exporting, plans/Quota/Comps, self-hosting, privacy FAQ), the styling-reference section appended from the engine's generator; `docs-content.ts` renders the combined source through the core renderer (math, Shiki, the app's mermaid hook) and generates the section nav from the rendered h2s, so nav and content cannot drift. `DocsPage` renders it at `/docs` (route + App switch): title and intro as chrome, prose in `docs.css` (token-based, dark-mode safe), nav stacked above the content on narrow screens and sticky to the side on wide ones. Entry points: a Docs link in the shared Footer, a Docs item in the AccountMenu in both its signed-in and signed-out states (docs-page spec). The launch workstream's docs-page ticket (`.scratch/launch/issues/02-docs-page.md`) is already marked superseded — footer and GitHub presence shipped with launch-chrome; the page work lands here. One item of that superseded list was not carried over: the "Save as PDF" walkthrough with screenshots (exporting is covered in prose in the Exporting section; screenshots would be a maintenance liability — revisit if wanted).
- The Stylesheet tab's footer line now carries a **Styling reference** link to `/docs#styling-reference` — a router `Link`, so the History-API swap keeps the open Document (verified end-to-end in Chromium: type → link → docs → back, marker intact). Verified pixel-level in Chromium at wide and narrow widths, light and dark: single-column prose, working tables, framed code blocks, in-page anchors.
- Design decision worth a human's eyes: the documented variables are a **read contract, not a theming API**. The generated rules keep their direct values; the variables mirror the settings-derived values so user CSS can align with them (`var(--mpdf-accent)`), and the reference says redefining one changes nothing. Making the generated rules consume the variables instead would let a Custom Stylesheet retheme by override — but the builder derives several colors from the accent by alpha-suffix (borders, rules, alert tints), which cannot go through a variable, so overrides would work for some properties and silently not for others. The honest, predictable half was chosen; flipping it later is a builder refactor plus a docs change, gated by the same drift test.

**Notes:** The page is designed by the docs spec at `.scratch/docs-page/spec.md` (one long page, section nav from headings, rendered from a single markdown source), and the content list to cover comes from the launch workstream's docs-page ticket — getting started, the page-break syntax, math and diagram examples, the font catalog, self-hosting, and the privacy FAQ. That ticket also described the footer and GitHub presence, which already shipped; its remaining page work is delivered here, so it should be marked superseded rather than implemented twice.
