# 09: The browser suite still reviews AI proposals on surfaces that no longer exist

**What to build:** The ten e2e tests that exercise the AI review path must be brought onto the surfaces that shipped. `035c7d8` ("review AI proposals in place, not in a modal") deleted `AiReviewDialog.tsx` and replaced it with `AiReviewBar.tsx` plus inline editor decorations; it updated the unit tests — two new files, one deleted, six edited — and **not one e2e spec**. Two assumptions in those specs are now stale, and between them they account for every failure on `main` today:

1. **The review surface testid is gone.** Ten references across three specs still ask for `ai-review-dialog`, which nothing renders. Nine of them sit in tests that now fail: 2 of 8 in `ai-command.spec.ts`, 6 of 7 in `ai-long-document.spec.ts`, 1 of 3 in `ai-stylesheet.spec.ts`.
2. **The Stylesheet tab's proposal card no longer echoes the CSS.** `ai-stylesheet.spec.ts:102` is the tenth failure and has nothing to do with the testid: it asserts the card contains the proposed rules, and the card now reads "A proposal is in the box above — review it there." The CSS moved into the box itself, where `StylesheetBoxDiff` draws it.

One of those ten references is worse than the nine failures. `ai-command.spec.ts:222` asserts `expect(page.getByTestId('ai-review-dialog')).toBeHidden()` in the test that a truncated reply is refused — and that test **passes**, because `toBeHidden()` is satisfied by an element that does not exist. It reads as "no proposal to review" and checks nothing at all.

This is not a rename. The old modal *displayed the proposed text*; the new design deliberately does not — the diff is drawn where the change will land. So the assertions that read a proposal out of a review surface have to move to wherever the proposal is now drawn, and only the ones that ask whether a surface is up or gone can be a straight swap.

**Spec:** `.scratch/ai-transforms/spec.md` (the review surface, as reshaped). The replacement surface is `apps/web/src/ai/AiReviewBar.tsx`; the editor decorations are `apps/web/src/editor/ai-review-decorations.ts`; the stylesheet diff is `apps/web/src/inspector/StylesheetBoxDiff.tsx`.

**Blocked by:** nothing. Independent of the open tickets; the pre-announcement checklist (`launch/06`) requires an all-green pipeline.

**Status:** resolved

- [x] All three specs drive the shipped review surfaces, and no spec mentions `ai-review-dialog`. — **Corrected, not satisfied as written.** The bar is the review surface for `/ai` only; `/ss` has never rendered one, so `ai-stylesheet.spec.ts` drives the stylesheet box's diff view instead (see Comments).
- [x] Assertions that read the proposal out of the review surface read it from the editor's decorations instead: the struck-through original is `.cm-ai-del`, the proposal is `.cm-ai-suggestion` (`.cm-ai-dimmed` when its per-change toggle is off). — The seven named assertions were in fact **nine**: the list missed `ai-long-document.spec.ts:263` and `:335`.
- [x] `ai-long-document.spec.ts:366`'s negative assertion — that a spent allowance is *not* announced before the pending proposal is decided — is re-pointed deliberately, not by reflex, and keeps the test's intent: an AI Action already counted must still be acceptable. — The test now asserts `ai-accept-reason` has **count 0** and that Accept is enabled. The original's copy-match was dropped rather than swapped: the string it looked for is rendered nowhere in the app, so it could never fail (see Comments).
- [x] `ai-stylesheet.spec.ts:102` asserts the proposed rules where they are now drawn — the Stylesheet tab's box (`stylesheet-box-diff` marking the change) — and asserts the proposal card's own content separately, so the test still proves the turn joined the conversation as well as the CSS arriving.
- [x] Visibility-only assertions are straight swaps, variable renamed from `dialog` to `bar`: `ai-command.spec.ts:117, 175`; `ai-long-document.spec.ts:194, 229, 259, 306`. — **`ai-stylesheet.spec.ts:195` is not one of them**: there is no bar to swap to, so that test was re-pointed instead.
- [x] `ai-command.spec.ts:222` is given something to assert. It names both surfaces that *would* have appeared had a proposal been made — the bar and `.cm-ai-suggestion` — and fails when either is present, by count rather than by `toBeHidden()`.
- [x] Each rewritten test is falsified before it is kept — break the behaviour it claims to cover and confirm it fails. — Six mutations, each reverted; every rewritten test failed against at least one.
- [x] `pnpm --filter @perfectmarkd/web test:e2e` reports the AI specs green. — **67/67**, performance project included, with no failure left in the run at all.

## Comments

- **Found while verifying launch/05** (2026-09-25), which ran the whole web suite and found ten failures unrelated to that work. Confirmed pre-existing by running the same three specs on a clean tree at `d4a218f`: identical ten failures.
- **The cause is a half-finished migration, not a whole one that was forgotten.** The same specs already use the replacement surface's testids — `ai-change-count`, `ai-review-plan-step` — and the new button label `Accept (1)`, which `AiReviewBar` renders and the old dialog did not. Whoever did the refactor migrated the assertions they noticed and left the rest. That is why the fix is smaller than ten rewritten tests and larger than a find-and-replace. The unit suite was migrated properly: `ai-command.test.tsx:614` asserts `queryByTestId('ai-review-dialog')` is *not* in the document, which is the correct way to pin a removal and should stay.
- **The vacuous assertion is the reason this is not just cleanup.** Nine of the ten references announce themselves by failing. The tenth hides, and a suite that fails loudly is at least honest about it; an assertion that reads as coverage and provides none is the one that lets a regression through. Expect the same pattern wherever a `toBeHidden()` was left on a removed testid — this ticket found one, and the fix should look for others rather than assume it is alone.
- **Why it matters more than ten red tests.** Those tests are the only place the AI path runs end to end in a real browser — trigger, popup, proposal, accept, reject, undo, the plan ladder, the allowance running out, and the Stylesheet tab's conversation. The unit suites cover `AiReviewBar`, the decorations, and the diff in isolation, so nothing has driven the assembled flow since the refactor. The suite being permanently red is the second problem: it trains the next person to skim past failures, which is how the following regression ships.
- **Ticket 08's green check was true when it was written, and is not now.** Verified at `5b3cd97`: `AiReviewDialog.tsx` existed and all ten `ai-review-dialog` references in these three specs matched it, so the suite was green when 08 closed. `035c7d8` invalidated it three commits later. 08's checklist item is annotated to say exactly that rather than unchecked, because unchecking it would misrepresent when the breakage happened — and this ticket is the work, not 08.
- **Not in scope here, filed separately:** `shell-compact.spec.ts`'s "the shell and its overlays keep the 44px floor at 320px" failed once under load and has not reproduced since — [launch/08](../../launch/issues/08-shell-compact-touch-floor-flake.md).

- **Implemented (ai-transforms/09).** Test-only: `apps/web/e2e/ai-command.spec.ts`, `ai-long-document.spec.ts`, and `ai-stylesheet.spec.ts`. No production file changed — apart from those three specs and this ticket, the tree is byte-identical to `HEAD`.

- **The ticket's parenthetical that `EditorPane` "renders one and feeds it `ai.review.command` for both `/ai` and `/ss`" is not true of the shipped code, so checklist item 5 was corrected rather than satisfied.** A stylesheet proposal has no bar to swap to: `EditorPane.tsx:341` gates the bar on `ai.review.command === 'markdown'`, `ai.hunks` is `null` for a stylesheet review, and `useAiCommand.ts:429-437` returns early for `command === 'stylesheet'`, so no review is opened at all. `ai-command.test.tsx:603-615` pins exactly that — it asserts *both* `ai-review-dialog` and `ai-review-bar` are absent after `/ss`. The spec agrees ("A stylesheet proposal is reviewed **in the stylesheet box**"); the surviving "the same proposal dialog" wording in §Where the stylesheet lives is stale spec text, not a description of the bar. Confirmed in the browser rather than reasoned about: the failure snapshot after submitting `/ss` shows the editor pane with no bar and no decorations, the Inspector still on Page, and the Document at 270 characters. `ai-stylesheet.spec.ts` therefore reviews the stylesheet where it is actually reviewed — `stylesheet-box-diff` in the Stylesheet tab, with that view's own Accept — and asserts that `/ss` itself moved no tab *before* the user goes there deliberately. The test still drives `/ss` end to end and still proves the box is written and the turn joined the conversation.

- **A third stale assumption, which the ticket's two did not cover, was hiding behind the dialog references.** `ai-long-document.spec.ts`'s first test failed at line 185 — before any of the ten references — on the original spec and on the rewritten one alike. `f9885cf` ("refine AI popup dismissal"), three commits after `035c7d8`, made any outside `pointerdown` dismiss the popup, and the `selectFirstCharacters` helper opened with `page.locator('.cm-line').first().click()`. That click *is* an outside press: the popup closed and the `/ai` trigger was restored (hence the 270 characters). The helper now focuses the editor without a pointer press; the selection itself is still made by real keystrokes. So "between them they account for every failure on `main` today" was optimistic — two assumptions explained nine of the ten tests, and this one explained the tenth.

- **The list of seven proposal-reading assertions missed two.** `ai-long-document.spec.ts:263` ("stops a plan partway") and `:335` ("rejects one step and carries on with the next") each read a proposal out of the review surface exactly as the named ones do. Nine, not seven. The code converted both, and the checklist is corrected above — but the ticket's inventory being two short is the same lesson as its own "look for others rather than assume it is alone": a hand-built list of stale assertions is worth less than a grep for the testid.

- **The audit for other vacuous `toBeHidden()`s found none.** Every testid the e2e suite asserts hidden or absent is otherwise asserted visible somewhere in the suite, so a renamed testid there would fail loudly; `ai-review-dialog` was the only dead one. The `ai-hint` and `ai-prompt` hidden-assertions are negatives about a surface that provably renders — the correct shape, and not this pattern. The family has a second member, though, and it was sitting in the very line this ticket pointed at: a negative assertion whose *string* the app never renders. That one is recorded below.

- **The re-pointed negative assertion needed a second half — and its original form was dead.** Two separate problems in the one line the ticket pointed at. First, `ai-accept-reason` is not rendered while Accept is available (the bar draws it only when `disabledReason !== null || checked.size === 0`), so asserting `not.toContainText` on it alone would have repeated the original mistake: a negative assertion against a locator that resolves to nothing passes vacuously. Second — found in review, not by the ticket — the string it matched, `No AI Actions left this period`, is rendered **nowhere** in the app; it survives only in ticket 07's record, which documents that the copy was deliberately moved off `acceptDisabledReason` and onto `retryBlocked` alone. A copy-match against a string the app no longer emits passes whatever the app does, so it was dropped rather than re-worded. The test now asserts `ai-accept-reason` has **count 0** and that Accept is enabled; the enabled Accept also proves the bar is up, because a missing bar resolves the button to nothing and fails. Together those say what the test meant: a spent allowance is not announced, and it does not block a proposal already counted.

- **Falsified before kept.** Six mutations, each applied, run against the affected specs, and reverted. Renaming the suggestion widget's class failed the six tests that read a proposal from the decorations; making the bar never render failed the eight tests that assert it; offering a refused reply as a proposal failed *both* of `ai-command.spec.ts`'s new count-0 assertions (bar: 1, suggestion: 1); announcing the spent allowance in `acceptDisabledReason` failed the allowance test at the re-pointed `ai-accept-reason` assertion; disabling the box's pending swap failed all three stylesheet tests; opening a review for `/ss` failed the new "no editor surface" assertion. One mutation run initially passed and was re-run rather than waved through — a fabricated empty target produced no hunk, so the mutation, not the assertion, was at fault. **The falsification was also not sufficient on its own**: the mutation that announced the spent allowance failed the re-pointed assertion only because it injected that assertion's exact wording into `acceptDisabledReason`. It proved the assertion bites *for that string*, not that the app ever emits it — and the app does not. A mutation that makes a dead assertion fail is not evidence the assertion was alive; that took reading the product copy.

- **Verified green**: `pnpm typecheck`, `pnpm lint`, and `pnpm --filter @perfectmarkd/web test:e2e` at **67/67** — the performance project included and no failure left in the run, so the `shell-compact` flake did not reproduce. The repo-wide unit suites are unaffected: no production file changed.

- **Environment note, not a code finding.** The suite's `webServer` build tripped this sandbox's bulk-delete guard — `tsup` cleaning `packages/core/dist` raised `SAFE_DELETE_BULK_CONFIRM_REQUIRED` and left the package's `dist` half-deleted, so the suite could not start at all. The runs above cleared `NODE_OPTIONS` and `CODEBUDDY_SAFE_DELETE_ENABLED` for the build step. On a normal machine this is a non-issue; recorded so the next agent does not read it as a broken build.
