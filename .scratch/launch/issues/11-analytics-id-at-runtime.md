# 11 — The analytics website id is baked at build time, so one published image cannot serve two instances

Status: resolved
Blocked by:

`apps/web/src/analytics/tracker.ts:48` reads `import.meta.env.VITE_ANALYTICS_WEBSITE_ID`, and Vite inlines `import.meta.env` at build time. `docker-compose.yml:31` passes it as a build arg, and `README.md`'s Analytics section tells the operator to set it in `.env` and **rebuild the web image** (`docker compose up -d --build caddy`).

That is correct while every deployment builds its own bundle, and it is what makes an empty id produce a bundle with no analytics at all — no tracker script, nothing collected (launch/01). It stops being correct the moment the caddy image is **pulled** rather than built (launch/10): one published image can carry neither the Admin's id (every self-hoster's page views would land in the Admin's Umami) nor an empty id (the Admin's own deployment would collect nothing). The id has to become a **runtime** input.

**What to build:** hand the id to the bundle at runtime instead of inlining it.

- Caddy serves a tiny generated script from the deployment's environment, e.g. a `handle /analytics-config.js` block whose `respond` interpolates `{$ANALYTICS_WEBSITE_ID}` into `window.__ANALYTICS_WEBSITE_ID__`. It must be `no-store` (never cached immutably like `/assets/*`) and carry `X-Robots-Tag: noindex` alongside `/export*`.
- `apps/web/index.html` loads that script in `<head>` **before** the module bundle, the way the theme-before-first-paint script already does — so `tracker.ts` reads a value that is already there and nothing about initialization becomes async.
- `tracker.ts` reads the runtime value in place of `import.meta.env`. An absent or empty value must keep today's behaviour exactly: `initAnalytics()` returns without requesting the script, `trackEvent`/`trackPageView` drop their calls. That property is the feature, not a fallback — assert it.
- `VITE_ANALYTICS_WEBSITE_ID` leaves `apps/web/Dockerfile`'s `ARG`/`ENV` and `docker-compose.yml`'s `build.args`; `docker-compose.yml` passes `ANALYTICS_WEBSITE_ID` to the **caddy service's runtime `environment`** instead. `VITE_ANALYTICS_URL` stays a build arg — it is a fixed `/analytics` on every instance.
- `.env.example` and `README.md` follow: the instruction becomes "set `ANALYTICS_WEBSITE_ID` and restart", not "rebuild". `README.md`'s closing line ("With no id set, the bundle loads no tracker and collects nothing") stays true and should be re-worded to say *instance*, not *bundle*.
- Tests: `analytics/tracker.test.ts` covers the id present and absent (the latter asserting nothing is sent); `App.test.tsx`'s two `initAnalytics` assertions stay meaningful. The e2e suite's analytics stub is unaffected — it mocks the module, not the value.

**Accepts:** one image pulled from GHCR collects analytics on an instance whose `.env` sets `ANALYTICS_WEBSITE_ID`, and collects nothing — no tracker request at all — on one that does not, with no rebuild in either case. The Admin's id appears in no published artifact.

**Notes:** this is a prerequisite for launch/10, not a nice-to-have. Publishing the image first would mean choosing between leaking the Admin's id into a public package and shipping an image that collects nothing on the instance it was built for.

## Comments

- Filed 2026-09-26, found while scoping the GHCR publish path (launch/10) for the Admin's "build the image once, pull it on the host" deployment plan.
- **Implemented** (2026-09-26). `tracker.ts` reads `window.__ANALYTICS_WEBSITE_ID__` in a `websiteIdFromConfig()` helper called from `initAnalytics()`, so the read is lazy and the config script only has to land before the first track; `TRACKER_BASE` still comes from `VITE_ANALYTICS_URL`. The Caddyfile serves `/analytics-config.js` from `{$ANALYTICS_WEBSITE_ID:}` with `Content-Type: application/javascript`, `Cache-Control: no-store` and `X-Robots-Tag: noindex`; the id left `apps/web/Dockerfile`'s `ARG`/`ENV` and the compose `build.args`, and arrived as a caddy runtime `environment` entry. `index.html` loads the config with `defer` before the module bundle. `.env.example` and `README.md` now say restart, not rebuild. The operator's local `.env` key was renamed too.
- **One addition the spec did not name:** `apps/web/public/analytics-config.js`. The new `<script>` tag needs a real file under `vite dev`, `vite preview` and the e2e bundle — without it the SPA fallback answers the path with `index.html`, which the browser then fails to parse as JavaScript. The file carries an empty id (so nothing leaks into a published image) and the Caddy route shadows it in the shipped deployment. The cost is a second hand-maintained copy of one assignment; the alternative — a Vite plugin serving the path in dev and preview — duplicates the contract just as much, and this way the file documents itself in the repo.
- **Verified, not assumed.** `caddy adapt` with the block moved to the *end* of the `(serve)` snippet still places it ahead of the SPA fallback — Caddy orders the mutually-exclusive `handle` group itself, so the file position is not the mechanism (the comment now says so). A live Caddy on `caddy:2` with the real Caddyfile returned `200`, the right content type, `no-store`, `noindex` and `window.__ANALYTICS_WEBSITE_ID__ = "test-id-1234";`; with the variable unset it returned `= "";`; `/pricing` still hit the SPA fallback and `/analytics-config.js` did not. The built `dist/` contains no trace of the local `.env`'s id. Unit suite 1,589 passed; web e2e 67/67.
- **Review findings taken:** the no-id test now asserts *nothing was appended to `<head>`* rather than only that no script element exists, so "sends nothing" is observed instead of implied — falsified by returning a fallback id, which failed exactly that test and its blank-id sibling.
- **Review finding declined, with reason:** the standards pass wanted a test binding the three copies of the assignment contract (Caddyfile, the public file, `tracker.ts`). No unit test can run Caddy, and a source-text assertion would be more fragile than the rename it guards; the three sites already name each other in comments, which is this repo's idiom for cross-file contracts.
- **Known limit, left as-is:** the id is interpolated raw into a JS string literal, so a value containing a quote would produce invalid JavaScript. Ids are bare UUIDs and `.env.example` says so. Escaping is not something Caddy's `respond` can do, and the value is operator configuration in the same trust domain as the Caddyfile itself.
