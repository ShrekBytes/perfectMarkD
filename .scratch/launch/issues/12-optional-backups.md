# 12 — Backups must be opt-in, and must work with or without a remote

Status: resolved
Blocked by:

`ops/backup.sh:50` hard-requires a remote — `: "${BACKUP_REMOTE:?BACKUP_REMOTE must be set in .env ...}"` — so a deployment that wants no off-machine copy cannot install the timer at all, and a run without a remote fails loudly instead of doing the part it can. The Admin's machine has no backup remote configured for this project (rclone carries `filen:` and `proton:`, neither pointed at PerfectMarkD), and the intent is that backups work *with or without* one rather than forcing a choice.

The script also cannot run as shipped on the deployment host: `ops/perfectmarkd-backup.service` hardcodes `WorkingDirectory=/opt/perfectmarkd` and installs as a **system** unit running as root, while the stack runs rootless under the user's podman — so a root-run `docker compose` cannot see the containers it is meant to dump. `ops/backup.sh` itself shells out to `docker compose`.

**What to build:**

- A `BACKUP_ENABLED` switch in `.env`, default `0`. At `0` the script exits 0 having done nothing — so an installed timer is harmless, and turning backups on later needs no systemd change. At `1` it runs as it does today.
- With `BACKUP_ENABLED=1` and **no** `BACKUP_REMOTE`: local-only. Dump the database with the existing `PRAGMA quick_check` verification, mirror the history directory, prune the staging dir by age, then stop — no rclone call, no failure. Same staging layout (`$BACKUP_STAGE/db/`, `$BACKUP_STAGE/history/`) so pointing a remote at it later uploads a consistent tree.
- With a remote set, the existing upload / `--backup-dir` / 30-day remote prune path runs unchanged.
- `.env.example` gains `BACKUP_ENABLED`; `BACKUP_REMOTE` and `BACKUP_STAGE` are already documented there (commented out, near the end), so only their "Unset = the backup job refuses to run" note needs rewriting for the switch.
- The unit: make it installable on a host that is not `/opt/perfectmarkd` and that runs rootless podman. Either ship it as a **user** unit (`systemctl --user`, with `loginctl enable-linger`) or document `DOCKER_HOST` pointing at the podman socket, and make `backup.sh` work when the compose driver is `podman compose`. Pick one and say why in the unit's comment; the current comment tells the operator to edit the path by hand and says nothing about the rootless case.
- `docs/ops/restore.md` follows: the prerequisites section states the switch, and says plainly that with backups disabled there is **no** recovery path — that is the trade the operator is choosing, and it should not be discovered at restore time.

**Accepts:** with `BACKUP_ENABLED=0` an installed timer is a silent no-op; with `1` and no remote it produces a verified dump and a history mirror under `$BACKUP_STAGE` and exits 0; with a remote it uploads and prunes as before. The unit runs against a checkout that is not `/opt/perfectmarkd` on a rootless-podman host and reaches the running api container.

**Notes:** the local-only path is the honest middle ground for the Admin's deployment — it costs nothing, needs no account, and covers "I deleted the wrong thing". A remote can be added later by setting one variable.

## Comments

- Filed 2026-09-26 from the Admin's decision: no remote backup for now, and the feature must not force one.
- **Implemented** (2026-09-26). `ops/backup.sh` gates on `BACKUP_ENABLED` (anything but `1`, unset included, exits 0 having created nothing) and treats `BACKUP_REMOTE` as optional: unset means dump + history mirror + staging prune under `$BACKUP_STAGE` and no upload. The unit became a **user** unit with `Environment=DOCKER_HOST=unix://%t/podman/podman.sock` and `WantedBy=default.target` — the "pick one" the ticket asked for, resolved as *both halves of the same choice*: a user unit is what rootless podman needs, and `DOCKER_HOST` is what lets `ops/backup.sh`'s `docker compose` calls reach the containers `podman compose` created. `docs/ops/restore.md` and `.env.example` follow.
- **Verified by running it, against a real api container.** A throwaway api container on the host (the existing one, started by `podman start`, so the image store was not touched): `BACKUP_ENABLED` unset → `backup: disabled`, exit 0, and the staging dir was never created; enabled with no remote → a 94 KB dump whose header is `SQLite format 3`, `quick_check ok` reported from inside the container, the history mirror staged, exit 0; enabled with a remote → upload, remote prune, `env/.env` copy, exit 0, with `db/` and `env/` landing in the remote tree. Then the pair the ticket is really about, with a PATH holding every tool the script needs *except* rclone: enabled + no remote **succeeded**, and enabled + remote **failed loudly** with the actionable message. `systemd-analyze --user verify` accepts the unit and expands `%h`/`%t` correctly.
- **A regression the review caught.** `docs/ops/restore.md`'s rehearsal builds its `.env` with a `printf` that listed four secrets and `BACKUP_REMOTE` — no `BACKUP_ENABLED`. With this change that rehearsal would have run `ops/backup.sh`, hit the new gate, done nothing, and died at `restore.sh` with "no database dumps found". The doc itself says "keep it green when you touch the backup scripts", so both `printf` lines now carry `BACKUP_ENABLED=1` and the `ops/backup.sh` line says why. Also fixed: `journalctl -u` → `journalctl --user -u` (the unit is a user unit now), and the "no recovery path" statement moved into the prerequisites section where the spec asked for it — plus a line in `.env.example`, where the switch is actually flipped.
- **A bug in my own comment, found by review.** I had written that "anything already exported wins" while `source`-ing `.env` afterwards, which made `.env` win. Rather than weaken the comment, the code now matches the intent: each key is exported only if it is not already set, the way compose treats `environment:` over `.env`. Verified end-to-end — with `.env` naming one remote and the environment another, the environment's won, and `.env` was restored byte-identical (checksum compared) afterwards.
- **Kept, with reasons.** (1) The unit's default checkout is `%h/self-hosted/perfectmarkd`, which does not exist on this host yet — the repo is at `~/Documents/GitHub/perfectMarkD`. A static unit cannot discover a checkout, the deployment layout is the documented one, launch/04 creates it, and `systemd-analyze verify` reports a wrong path plainly at install time. (2) The disabled mode prints one line per night. The ticket says "silent no-op"; read as *no side effects* — it exits before `mkdir` — the line is kept because it is the difference between "deliberately off" and "silently broken" in journald. (3) Local-only does not stage `.env`: the ticket's list does not include it, and that copy exists to survive losing the host, which local-only cannot promise. (4) Local-only loses history deletions after the next run, because the mirror is rebuilt from scratch and `history-prev` is an rclone feature. Recorded in the script header and in `restore.md` rather than inventing a fourth mode.
- **Host side effects from the verification**, all reverted: `podman.socket` started (needed by any `podman compose` work; linger was already on), the api container started and stopped, and the local api image briefly tagged as the GHCR ref before being put back under `docker.io/library/perfectmarkd-api:latest`. The container's recorded `ImageName` still names the unpublished GHCR tag — cosmetic, and launch/04 recreates it.
