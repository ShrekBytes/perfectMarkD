# 04 — Deploy on the Admin's machine behind a Cloudflare Tunnel

Status: ready-for-agent
Blocked by: server/06, launch/03, launch/10

Serve the Compose stack (caddy + api + umami) from the **Admin's own machine**,
published at the real domain through a **Cloudflare Tunnel**. Nothing in the
application changes: Caddy keeps serving plain HTTP on `:80` inside the compose
network and the tunnel publishes that origin; TLS terminates at Cloudflare's
edge, so Caddy's automatic ACME TLS is unused in this deployment. The Admin
connects and configures the tunnel and DNS themselves — **tunnel setup is not
part of this ticket**, and an agent should not write instructions for it.

Remaining work on the host machine:

- Check the repo out at `~/self-hosted/perfectmarkd` and bring the stack up by **pulling** the published images (launch/10) — `podman compose pull && podman compose up -d --no-build` — with `SITE_ADDRESS=:80` and the domain reachable through the tunnel. Nothing is built on this machine.
- Confirm Server Export works from the public origin — the worker loads the SPA's `/export` page over the compose loopback (`EXPORT_ORIGIN=http://caddy`, already the shipped default), not the public URL, so this is a verify-on-the-real-host step rather than a change.
- Log rotation, restart policy, and the SQLite WAL checkpoint job — **investigated, and none of the three needs work** (see Comments for the evidence). Containers log to journald, which self-bounds and vacuums; all four services already carry `restart: unless-stopped`; and the WAL bounds itself at SQLite's default auto-checkpoint. **No uptime monitoring** (decision, 2026-09-26): no Uptime Kuma, no healthchecks.io, no alert channel — the stack is expected to be looked at, not paged about.
- Backups: install the launch/03 timer as a **user** unit and leave it governed by `BACKUP_ENABLED` (launch/12). No remote for now — local-only is the accepted state, and it must not be forced.
- Host realities a VPS would have handled for you: disable sleep so the machine stays awake, make the stack **actually come back after a reboot** (see Comments — it currently would not), and prove it with a reboot.
- Runtime knobs: `EXPORT_CONCURRENCY`, `EXPORT_BURST_PER_MINUTE` and `EXPORT_RENDER_TIMEOUT_MS` are read by `apps/server/src/env.ts` but were never forwarded by `docker-compose.yml`, so setting any of them in `.env` did nothing at all. **Fixed** — compose now passes all three as empty-default passthroughs (so the numbers stay in `env.ts` and nowhere else), and the deployment sets `EXPORT_CONCURRENCY=1`: the default of 2 puts two headless Chromium renders in flight on a host with ~2 GB free.

**Accepts**: `https://<domain>` serves the app from the Admin's machine; Client Export and Server Export both complete end-to-end from the public URL; a reboot brings the stack back with no intervention.

## Comments

- **Hosting decision (user, 2026-09-23)** — supersedes the 2026-09-13 AWS note below: launch runs on the Admin's own machine, published by a Cloudflare Tunnel at the real domain (ADR-0010). Why: no server rent before there is revenue; the machine is already the dev/prod-parity environment (Chromium, the Compose stack, and rootless podman all verified there); and an outbound tunnel needs no port forwarding, no static IP, and no inbound firewall rules, so the home IP is never exposed. Trade-offs accepted: the service is up only while the machine is up, home upload bandwidth caps Server Export throughput, and all user traffic passes through Cloudflare's edge — a third party in the path that the app itself makes no requests to, which the Privacy page should state plainly rather than leave implied by the "no third-party analytics" line. The VPS move is deferred, not rejected; see ADR-0010 for the revisit triggers.
- **VPS path, deferred**: the AWS EC2 t4g.micro paid by GitHub Student credits (ARM Graviton, 2 GB, swapfile, `EXPORT_CONCURRENCY=1`) remains a viable box when the move happens, alongside a €4–5/mo Hetzner instance. launch/03's backup/restore flow is the migration path in either case — a clean-machine restore onto the new host.
- **Chromium is done** (commit 59fd5b3): headless Chromium baked into the api image (`playwright install --with-deps --only-shell chromium`, browsers at `/ms-playwright`) — pulled forward from this ticket at the user's call so local testing is production parity for every feature. Verified in the local compose stack: a Premium job rendered a 2-page PDF through the baked browser (`status: done`, auto-stored in Export History). This ticket keeps only the host-side work: stack up, tunnel-fronted domain, monitoring, log rotation, restart policy, backups remote.
- From server/06: the shipped Caddyfile's automatic ACME TLS path (`SITE_ADDRESS=<domain>` with the Cloudflare DNS record proxy-off) is **not used in this deployment** — the tunnel terminates TLS and Caddy stays on plain `:80`. That path stays documented in the Caddyfile for a directly-exposed host, so a future VPS move can use it unchanged.
- **Deployment decisions (Admin, 2026-09-26)** — the deploy becomes a pull, not a build:
  - **The host pulls published images.** Checkout at `~/self-hosted/perfectmarkd`; the stack comes up from GHCR with `podman compose pull && podman compose up -d --no-build`. That is a new prerequisite, filed as launch/10 (and launch/11 behind it, because the analytics website id is currently a build-time value and a published image cannot carry an instance's id). This ticket is now blocked by launch/10.
  - **The public host is `perfectmarkd.00022000.xyz`**, a hostname on the Admin's existing Cloudflare Tunnel. The subdomain does not exist yet; the Admin creates it. Tunnel and DNS remain the Admin's work, as the body already says.
  - **Tunnel origin is the host's `CADDY_HTTP_PORT`**, which `.env` already sets to `8901` — nginx holds `:80` on this machine. The port choice itself is not load-bearing.
  - **`api-data` may be wiped.** The volume currently holds the previous stack's database and encrypted history; a clean start is acceptable, so a fresh `HISTORY_ENCRYPTION_KEY` is fine and no migration is needed.
  - **No monitoring.** The Uptime Kuma / healthchecks.io bullet is dropped, along with the alert clause in Accepts.
  - **Backups are local-only and optional**, governed by a switch — filed as launch/12. No remote account.
  - **`sudo` is available** if a step needs it, though podman and cloudflared both run without it.
  - **AI is active** at launch (`AI_API_KEY` is set in `.env`), so launch/06's AI prerequisites apply.
- **Host state verified 2026-09-26** (the deployment target is this machine, `abyss`): `podman compose` delegates to the docker compose plugin v5.5.1 and needs `unix:///run/user/1000/podman/podman.sock`, which does **not** exist while `podman.socket` is inactive — `systemctl --user enable --now podman.socket` is step zero. `Linger=yes` is already set. The four `perfectmarkd-*` containers exist but are exited (~21 h). 7.5 GB RAM with ~2.3 GB available and swap already at 3.3/7.5 GB; 40 GB free of 178 GB. It is a laptop (`BAT0`), so disabling sleep is real work. Neighbours not to disturb: nginx, `vaultwarden`, `dash-dash-dash`, and the active `vaultwarden` tunnel.
- **The pull path is proven on this host, not just planned** (2026-09-26). launch/10 shipped, the Admin pushed and made both packages public, and `podman compose pull && podman compose up -d --no-build` was run here: all four refs pulled with no registry credential, the stack came up with api/umami/umami-db `healthy`, and `/healthz`, `/` and `/pricing` all answered `200` on `:8901`. So this ticket's remaining work is genuinely the host-side half — tunnel, the boot mechanism, backups, sleep, reboot — and not the stack itself.
- **Caveat for the deferred VPS path**: the published images are `linux/amd64` only, and the `t4g.micro` named below is arm64. Either publish multi-arch or build on the new host before the move; do not assume the pull works there.
- **Corrected: there is no podman daemon, and the boot problem is different from how this ticket first stated it** (Admin, 2026-09-26). The body used to say "confirm the Docker service itself starts on boot", which is wrong for podman — podman is daemonless, and the systemd-shaped answer is what the Admin named: units, or Quadlet. The concern survives the correction, in a sharper form.
  - `restart: unless-stopped` **is** on the containers (`podman inspect … RestartPolicy.Name` → `unless-stopped` for all four), but a restart policy is not a boot mechanism on a daemonless runtime.
  - **Nothing starts this stack at boot.** `podman-restart.service` — the shipped unit whose `ExecStart` is `podman start --all --filter should-start-on-boot=true` — exists in both system and user scope and is **disabled in both**. Nothing in the user or system manager references `perfectmarkd`.
  - **The Admin's other services do come back, because systemd owns them.** `~/.config/containers/systemd/` holds symlinks to `vaultwarden.container`, `dash-dash-dash.container` and `copyparty.container`, each living in its own `~/self-hosted/<name>/` directory with `%h/self-hosted/<name>` volumes, an `EnvironmentFile=%h/self-hosted/<name>/.env`, `AutoUpdate=registry` and `WantedBy=default.target`; the generator produces `vaultwarden.service` and `dash-dash-dash.service`, both `active running`. PerfectMarkD is the one service on this machine with no such unit, so it is the one that would be missing after a reboot.
  - **So the deployment root convention is already settled by precedent**: `~/self-hosted/perfectmarkd/`, holding the checkout, its `.env` and whatever unit file this ticket ends up using, symlinked into `~/.config/containers/systemd/` if Quadlet is the choice. That is the answer to the "second clone or move" question the ticket left open.
  - **Three ways to fix the boot, and it is a real choice rather than a detail** — recorded so it is decided deliberately:
    1. **A user unit that runs `podman compose up -d --no-build` at boot.** Keeps `docker-compose.yml` the single definition (which launch/10 deliberately established, and which `README.md` and `docs/ops/restore.md` both document for self-hosters), and reconciles the running stack with the file on every boot. Needs `podman.socket` and `DOCKER_HOST`, both of which are needed anyway.
    2. **`systemctl --user enable podman-restart.service`.** One command, no new file, and it honours the restart policy already declared in the compose file. It would **not** disturb the other two services: their policy is `no` (systemd owns them), so the `should-start-on-boot` filter skips them. What it does not do is reconcile with the compose file — it restores the containers as they were created.
    3. **Quadlet, matching the machine's existing pattern.** Per-service units, dependency ordering, `AutoUpdate`. The cost is that it duplicates the four-service stack definition and creates a second thing to keep in sync with `docker-compose.yml` — which is the reason to hesitate rather than the reason to refuse.
  - Whichever is chosen, the acceptance is a reboot, and that is the Admin's to run.
- **Three checklist items closed by investigation rather than by building something** (2026-09-26). Each was in the body as work to do; two are already true and one would have been busywork:
  - **The SQLite WAL checkpoint job is not needed, and that is measured.** The app sets `journal_mode = WAL` and never touches `wal_autocheckpoint` (`apps/server/src/db/database.ts:30`), so SQLite's default of 1000 pages applies. Reproduced against a scratch database with exactly those pragmas: across 50,000 rows in 5,000-row batches the WAL grew to 4,420,792 bytes and then **plateaued** while the main db kept growing (4 KB → 8.6 MB) — auto-checkpoint firing at the threshold. The WAL only runs away under a long-lived read snapshot, and the server holds one connection and no long read transactions. A nightly `wal_checkpoint` timer would have been a job that never had anything to do.
  - **Log rotation is journald's, and it is already bounded.** `LogConfig.Type` on the api container is `journald`, `/etc/systemd/journald.conf` is entirely default (nothing uncommented), and journald bounds itself and vacuums — current usage 47.8 MB against 40 GB free on the journal's filesystem. Nothing to configure unless a tighter cap is wanted.
  - **The restart policy is already in the compose file**: `restart: unless-stopped` on all four services. The part that is *not* handled is the daemon itself starting on boot, which stays in the host list above.
- **The runtime-knob pass-through is fixed and falsified** (2026-09-26). `docker-compose.yml` now forwards all three, and `podman compose config` shows `EXPORT_CONCURRENCY: "1"` with the other two empty — the empty default reaches the server as empty, `nonEmpty()` returns null, and `env.ts` applies its own number, so there is still exactly one place the defaults live. Falsified rather than assumed: setting `EXPORT_CONCURRENCY=0` made the api container **refuse to boot** with `Error: Invalid EXPORT_CONCURRENCY: "0" — expected an integer ≥ 1`, which is only possible if the value is reaching `loadEnv` and not merely sitting in the container's environment. Restored to 1 and the stack came back healthy with `/healthz` 200.
