# 04 — Entitlement enforcement + unlock wiring

Status: resolved
Blocked by: server/04, billing/02

Single source of truth for gates: `GET /api/me` → {plan, expiry, quota, flags}. Apps/web: feature-flag store consumes it; the five gated Inspector controls unlock (🔒 → enabled) for active Pro/Premium; expiry handled (graceful re-lock + clear notice, no data loss — settings persist, just gated again). Server Export dropdown item replaces "coming soon" with quota chip + Premium queue-priority note. Over-quota/expired export attempts → typed error + upgrade prompt. Free logged-out users never gain gates (flags default locked).

**Accepts**: verify → gates open within one `me` refresh; expiry → re-lock; quota chip accurate; logged-out = locked.

## Comments

Implemented 2026-09-12 (commit `d1a7f63` + review fixes).

- **Server flags** (`apps/server/src/flags.ts`, new): the gated-feature vocabulary — the five controls of billing/spec.md §Gated features as booleans — and `featureFlagsFor(plan)`: open exactly while an Entitlement is active. `/api/me` (me.ts) now returns `flags` alongside plan/expiry/quota, so the payload is the ticket's {plan, expiry, quota, flags} single source of truth. Deliberate reading: flags are plan-gated, not allowance-gated — a comped user without a plan (billing/03) spends comps on Server Export but gains no features, because the gate is the plan itself. Tests: free/pro/premium/expired/comped flag matrix in me.test.ts (9).
- **Web flag store** (`apps/web/src/auth/flags.ts` + account-store): the "feature-flag store" is the account store's `flags` slice — /api/me is the single source of truth and the account store is its mirror, so a separate zustand store would only duplicate it and could drift (the codebase's recurring anti-pattern). `useFeatureFlags()` is the read API; `LOCKED_FLAGS` is the default before the payload lands and after sign-out. Two related restructurings: `quota` moved from the entitlement slice to a top-level account-store slice (comps grant allowance without a plan, so quota is account state, not entitlement state — server/04's own finding; QuotaChip's visible behavior unchanged), and `ApiError` now carries the server's typed `code` alongside the message (errorFrom parses it; auth/billing/admin callers unaffected).
- **Inspector unlock** (`controls.tsx` `GateImagePicker` + tabs): the gates read `flags` off `TabProps`. Custom page size: the Custom… option selects and the W×H inputs go live end to end. Background image and both banner bands: real uploads through the document store's asset ingest (editor-app/08) — pick → `asset://` ref → the engine renders it; replace/remove; ingest failures surface inline (same wording as the editor's paste path); background fit/scope/opacity go live with the gate. Locked rendering is byte-identical to Phase 1.
- **Interpretation note (fonts/stylesheet)**: those two gates render "Included with your plan" when unlocked instead of an enabled control — their real UIs (font upload + CSS textarea) are billing/05's entire scope, and an enabled-looking dead upload would lie harder than an honest note. The flags for both are live server-side; billing/05 only builds the UIs and reads the same `useFeatureFlags()`.
- **Server Export** (`serverExport.ts` + `useServerExport.ts` + ExportSplitButton): the dropdown item shows the quota chip (`used/limit`, danger when exhausted) plus the queue-priority note (Premium: "Priority render queue"; Pro: "Premium renders first"; comped: "Admin-granted exports"), and runs the real flow — build payload (same engine pipeline as preview/Client Export; every asset ref incl. banner/background resolved to data: URIs; client pageCount for the cap check), `POST /api/export`, poll the job, download the PDF, then kick an account-store `refresh()` so the chip shows the spend without a reload. The item stays "Paid" → pricing modal for Free/signed-out (acceptance: logged-out = locked; the ticket's "coming soon" actually shipped as "Paid" in billing/01 — both are gone for entitled users).
- **Typed errors + upgrade prompt**: the flow always attempts the export and lets the server decide (a stale chip may undercount freshly granted comps), then maps the verdicts: 402 `quota_exceeded` and 403 `entitlement_required` show the server's message as a toast AND open the pricing modal (the upgrade prompt), each after a `refresh()` — 403 re-locks stale gates immediately (expiry between refreshes), 402 syncs the chip. 429 burst, 413 payload, and job failures (render_failed/render_timeout/page_cap/worker_restart/pdf_gone) surface their messages without a prompt.
- **Expiry handling**: a refresh that re-locks a previously-active Entitlement while still signed in raises `planEndedNotice` → a dismissible shell banner ("Your paid plan has ended — paid features are locked again. Your documents and settings are untouched." + See plans link; the neutral wording covers admin revocation too). No data loss by construction: settings live per-document in IndexedDB and the locked rendering previews the persisted values. A 60s watchdog refresh in AppShell re-locks long-lived tabs (Plan Expiry is a date, not a session event — without it the gates would only re-lock on some user action).
- **Deliberately left out, with reasons**: a standalone flags settings key (nothing asks for admin-editable flags; derivation from the plan is the product rule — self-hosted instances get it for free since their server decides); per-file test-helper dedup (mePayload/jsonResponse helpers are test-local, each pinned to its file's shape); typing `plan` as a union server-side (the entitlements row column is text; the derivation must tolerate what the DB returns). Review findings folded in: test title de-jargoned ("extension", not "renewal" — CONTEXT.md Plan Expiry); `OPEN_FLAGS` shared from auth/flags.ts instead of redeclared across three test files; the header/footer banner blocks extracted into one `BannerImageField` so the bands can't drift; the unused `phase` state trimmed from useServerExport (only `busy` was ever consumed). One review finding rejected: "gates don't open within one me refresh after login" — false positive, `signedIn()` already fires the background recheck (server/04) and the standalone AuthPage calls it before navigating.
