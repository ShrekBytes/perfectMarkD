# 02 — Admin panel: payments queue + audit log

Status: resolved
Blocked by: server/01, billing/01

`/admin` shell (admin-gated, same design language, utilitarian). **Payments**: pending queue with full Order details (user, plan, duration, coin/network, txid as explorer deep-link per network, claimed vs expected amount, Reference Code), actions: **Verify** (preset durations or custom expiry; extending an active Entitlement stacks from current expiry) / **Reject** (reason). Decided Orders listed with filters. **Audit log**: every verify/reject/settings change with timestamp + admin + before/after. Reject reasons surface in the user's Upgrade status view.

**Accepts**: verify grants correct Entitlement (incl. stacking math); reject records reason; audit entries written; explorer links correct per network.

## Comments

Implemented 2026-09-11 (commit `03ad2d4`).

- **Server** (`apps/server/src/admin/`): `adminRoutes({ now })` mounted at `/api/admin` with an `isAdmin` gate middleware (401 anonymous, 403 non-admin) in front of every route. `GET /orders` lists every Order (newest first) joined with the user's email and their current Entitlement — what a duration grant stacks onto — reusing `orderView` (now exported from orders/routes.ts) so the admin view can't drift from the user's. `POST /orders/:id/verify` and `POST /orders/:id/reject` each decide the Order inside a `db.transaction` that also writes the audit entry, so a decided Order and its audit record (and, for verify, the Entitlement grant) land together or not at all.
- **Grant semantics**: exactly one of `durationMonths` (1/3/6/12) or `expiresAt`. Stacking lives in pure `admin/entitlement.ts` (`addMonths` with UTC month-end clamping — Jan 31 + 1mo → Feb 28; `expiryForGrant` — base = current expiry while it is strictly in the future, else now). Custom expiry sets the date exactly (no stacking — the Admin picked an absolute date); a date-only string runs through the **end of that UTC day**, since "good until 2027-01-05" should cover the 5th. A verify on an Order for a different plan than the current Entitlement takes the Order's plan and still stacks from the current expiry (spec defines one active Entitlement per user and stacking purely by expiry date). Verifying an Order with **no submitted txid is refused (409)** — nothing on-chain to compare; rejecting such an Order stays allowed (useful to tell the user why). Grant bodies with neither/both/bad values → 400; decided Orders → 409.
- **Reject**: requires a non-empty trimmed reason (≤1000 chars, same cap as notes); sets status/rejectReason/decidedAt; the reason already surfaces in the user's Upgrade status view (shipped in billing/01, `UpgradeStatusDialog`), and resubmission amends the same Order back into the queue.
- **Audit log**: new `audit_logs` table (migration `0002_medical_the_hunter`) — timestamp, admin identity, action (`order.verify`/`order.reject`/`settings.update` for billing/03), target, JSON before/after. The admin identity is snapshotted and `admin_user_id` is deliberately a plain integer, **not** a foreign key: deleting an account must not be able to erase the record of what was done. `GET /audit` returns the trail newest-first; the panel renders each entry with before/after JSON.
- **Web** (`apps/web/src/admin/`): `/admin` route (router `Route` union + `App` switch), `AdminPage` gated through the account store (signed-out → sign-in link; non-admin → not authorized), tabs **Verification** / **Audit log**, same design tokens, utilitarian dense rows. `VerificationQueue` defaults to the pending filter (with per-status counts), shows full Order details — email, Reference Code, plan·duration, coin/network, claimed vs expected with a danger-highlighted mismatch (`amountsMatch` compares numerically so `3` and `3.00000000` match), txid as an explorer deep-link (`verification-display.ts`: Tronscan for TRC-20, BscScan for BEP-20, Blockchair for Litecoin), the ≈USDT total for LTC orders from the captured rate, and Verify/Reject actions opening `VerifyDialog` (duration presets or a custom date, with a stacking-aware preview of the resulting expiry) and `RejectDialog` (reason required). Order-status labels/badges moved to `billing/payment.ts` so the user's status view and the admin queue can't drift.
- **Deliberately left out, with reasons**: settings-change audit rows (nothing writes settings until billing/03; the table and `settings.update` action are ready for it); sharing `addMonths`/stacking math between server and web (the web copy is a preview only, the server's grant stays authoritative, and both sides are pinned by worked-example tests — a new shared package for one function buys less than it costs); a shared `decideOrder` helper (verify and reject differ too much for the coupling to pay); audit-list pagination and per-row entitlement query batching (single-operator scale).
- **Tests**: server 28 (gate matrix, queue views incl. entitlement state, stacking/expired/custom/plan-change grant math against a fixed clock, txid guard, double-decide 409s, validation matrix, audit write+read with before/after) + pure math 9; web 22 (explorer links per network, amount match/mismatch, LTC ≈USDT, filters, verify/reject flows with refresh, dialog gating/errors, admin gating + tabs) + display helpers 11. Full suite 725 green; typecheck, eslint, prettier clean. Two-axis code review ran on the diff; findings folded in (vocabulary rename to "Verification", timestamp-based stacking note, shared `orderDate`).
