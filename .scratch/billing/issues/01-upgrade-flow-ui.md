# 01 — Upgrade flow UI (plan → Order → submitted)

Status: resolved
Blocked by: editor-app/09, server/02

Wire the pricing page/modal CTAs to the real flow: plan + duration select → register/login if needed → `POST /api/orders` → instructions view: amount, Reference Code, wallet address (copy buttons), network warning ("send only USDT-TRC20 to this address"), LTC rate note → "I've sent the payment" form (network, txid, amount, optional note) → pending state. "Upgrade status" entry point (top-bar user menu) lists the user's Orders with statuses + reject reasons; resubmission amends a pending/rejected Order. Replace the Phase-1 "coming soon" state.

**Accepts**: full happy path to a pending Order; copy buttons; validation (txid format, amount > 0); statuses display.

## Comments

Implemented 2026-09-11 (this commit).

- **Server** (`apps/server/src/orders/`): `POST /api/orders` (plan + durationMonths + paymentMethod → 201 with the Order), `GET /api/orders` (caller's own, newest first), `POST /api/orders/:id/submission` (first submission and resubmission are the same amend operation: details replaced, `status → pending`, `rejectReason`/`decidedAt` cleared — a 409 guards verified orders, and other users' orders 404). Reference Codes are `PM-` + 5 chars from an unambiguous alphabet (no 0/O, 1/I/L), generated with rejection-sampled random bytes; the UNIQUE index arbitrates collisions and the insert retries. Errors follow auth-route conventions (400 `{error}` human-readable, 401/404/409/503).
- **Amount semantics — deliberate reading of the spec**: the spec line says "exact amount (USDT-denominated; LTC amount computed from a rate captured at Order creation and shown alongside)". The schema has one `amount_expected` string whose comment demands it round-trip exactly what the user saw and what the Admin compares on-chain — and for an LTC order the on-chain comparison is the LTC amount. So `amountExpected` is **denominated in the order's coin** (USDT orders in USDT, LTC orders in LTC, computed at creation from `prices[plan].durations[duration]` ÷ captured rate, 8-decimal LTC precision via `orders/amounts.ts`), with the rate itself stored in a new `orders.ltc_rate_usdt` column (migration `0001_good_surge`) so the conversion stays explainable forever. The USDT total is display-only ("≈") on the client, derived from the stored pair. billing/02's "claimed vs expected" comparison inherits a per-coin-consistent basis. Sign-off on this reading is the one place the implementation bends the spec's wording.
- **Payments not configured ≠ error state**: wallets and the new `ltc_rate_usdt` setting seed empty/absent (same philosophy as server/01 — nothing ships pointing at a placeholder wallet), and order creation returns 503 "not set up yet" per method until the Admin sets them (billing/03's settings panel maintains both).
- **Coin/network coherence** (spec-review finding): a submission's network must be able to carry the order's coin — LTC orders only `mainnet`, USDT orders `TRC20`/`BEP20` — enforced server-side (`payment.ts` `networkValidForCoin`) and mirrored client-side where the form only offers the coherent networks.
- **Web** (`apps/web/src/billing/`): `UpgradeFlow` is a five-step state machine (details → auth → instructions → payment → submitted) used by both entry points; `PaymentInstructions` (amount, Reference Code, wallet, each copyable via `CopyButton`, plus the network warning in danger styling) and `PaymentForm` are shared with the status dialog. `PricingPage` opens `UpgradeDialog`; `PricingModal` swaps the flow into its own chrome (no stacked dialogs). Resubmission prefills the details being corrected (spec-review finding — "corrected details", not retyping blind). "Upgrade status" lives in a new top-bar `AccountMenu` (signed-out: Sign in link; signed-in: menu with the email, Upgrade status, Sign out), backed by a small `account-store` zustand store that `UpgradeFlow` also reads so the flow works from `/pricing` outside the shell.
- **Refactors the work pulled in**: `AuthForm` extracted from `AuthPage` (mode switch falls back to `/login`↔`/register` navigation on the page, in-place toggle in the dialog); shared `api/client.ts` (`ApiError`/`postJson`/`errorFrom` — auth keeps an `AuthError` alias); shared `shell/Dialog.tsx` chrome (pricing modal, upgrade dialog, upgrade status); shared server helpers `request-body.ts` + `db/sqlite-errors.ts` (de-duplicated from `auth/routes.ts`); `planName()`/`priceForDuration()`/`DURATIONS` in `pricing/plans.ts`; `BILLING_LIVE`/`COMING_SOON_NOTE` deleted. Export menu's Server Export hint reads "Paid" now that the flow is real.
- **Deliberately left out, with reasons**: per-order wallet snapshot (wallets are re-resolved at view time — billing/03's wallet-change guard + audit log are the designed answer to rotation); rate limiting on order creation (authenticated route, unlike auth's pre-account endpoints; the Admin queue in billing/02 is the abuse surface); `GET /api/prices` (the client catalog mirrors the server seed for display only — the Order response carries the authoritative amount).
- **Tests**: server 32 (routes: create/list/submit, pricing math incl. 12-month 10×, LTC rate capture + 503s when unconfigured, submission validation matrix, amend/resubmit/verified-409/cross-user-404, coin↔network coherence), web 40+ (flow happy path from signed-in and signed-out states with in-dialog registration, copy buttons against a stubbed clipboard, LTC rate note, client + server validation paths, status list/resubmit/prefill/empty/error-recovery, account menu, plan CTAs). Full suite 662 green; typecheck, eslint, prettier clean. Two-axis code review ran on the diff; its findings are folded in above.
