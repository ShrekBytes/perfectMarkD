# The Rate is fetched by a job, and the Admin cannot set it

The Rate — the USDT-per-LTC figure a customer converts a price by before starting an LTC Order — is written only by a scheduled job. Every twelve hours it fetches Kraken's public ticker for the LTC/USDT pair, validates the answer, and stores the figure beside the timestamps that say how far to trust it. The admin settings `PUT` refuses the Rate key outright, with a 403 naming the fetch, so "the Admin cannot choose the number a customer is quoted" is enforced by the server rather than by the absence of a form field. The panel reports the current figure, its age, and the last error, and offers no control to change any of them.

It was a number the Admin typed. Two things follow from that. A Rate set once and forgotten quotes customers wrongly, and the failure surfaces only when someone underpays and gets rejected. And an Admin who can set the Rate can set it to whatever suits them, which for someone converting a figure before committing is a trust problem before it is a convenience problem. No other setting has that property: a plan price is the Admin's to set by design and a wrong wallet address loses money, but neither puts the operator's judgement inside a quote.

The feed is keyless, public, and the only new outbound request the instance makes. It carries no credential, no user data, and no reference to any account — it is a price query for a pair, and two requests from two different instances are indistinguishable. The endpoint sits behind an `LtcRateProvider` interface resolved in the composition root, exactly as the AI provider (ADR-0008) and the identity exchange are, so nothing outside one file learns it and no test touches the network. The pair is LTC/USDT rather than LTC/USD because the Rate is denominated in USDT and no conversion belongs in the middle of a quote. The Privacy page names the feed for what it is; its no-page-loads claim keeps its precise scope and stays true, because this is a server-side request rather than a page load and it carries nothing about a visitor.

Validation refuses, and never clamps. A non-positive, missing, or non-finite value is rejected outright. A value more than 50% from the last good Rate is rejected as a provider fault rather than a market move — but only while that last good Rate is under 24 hours old, because after a longer outage the band is the wrong instrument: a real 50% move may have happened while nothing was fetching, and the maximum age is what should act. The first fetch has nothing to compare against and skips the band entirely, which is also how a Rate typed by hand before this job existed is treated — still quoted, because refusing it would switch LTC off on a method that is already configured and being paid in, but never used as a comparison. Once the Rate passes 48 hours, new LTC Orders are refused with their own message: "LTC payments are not set up yet" is correct for an unset Rate and wrong, alarming, and false for a feed outage, so the two refusals say different things. A failed fetch never clears the Rate — the last good figure keeps standing, its age keeps growing, and the maximum age is what finally acts on it, which is the whole reason for keeping it. Three timestamps live with the Rate inside its own stored value rather than the settings row's `updated_at`, so a failing job is distinguishable from a fresh one and the Rate and its age cannot drift apart. A successful fetch writes no audit entry: twice a day is roughly 700 a year and would drown the entries that matter, so change is logged at info level and only a failure or a validation rejection earns an audit entry — that is the state a human needs to find later.

The staleness policy stops where it stops, and the consequence is stated rather than hidden. The bound applies at quote time only. Re-checking it at Verification would mean either rejecting a customer who paid the figure they were quoted or re-pricing them after the fact, and both are worse than the exposure accepted here: an Order verified up to six hours after creation can be quoting a Rate up to 54 hours old. A fresher guarantee needs a refresh on read or a much shorter window, not a longer one. Trade-offs accepted: a Rate is only as trustworthy as a public ticker, and the band and the maximum age bound the damage without detecting a feed that is consistently and plausibly wrong; a Self-Hoster who wants a different feed edits one file and one constant, while one who wants a different policy has to change this decision, because the policy is the point; and the Admin can no longer rescue LTC payments by typing a rate — the fix for a bad Rate is fixing the feed. Rejected alternatives: keeping the field with a "fetch now" button, since a button that fills a writable field is a writable field; storing a flagged outlier anyway, since a flag every reader must check is the weakest link; rejecting every outlier with no age limit on the band, since after a multi-day outage the job would refuse the first honest rate it saw and leave LTC switched off long after the feed recovered; and fetching on read, which turns a price page into a request that can fail.

## The Payment Window

Every Order carries a Payment Window of six hours, fixed at creation. It bounds how long a quote stays payable, which is what stops a frozen figure being presented days after it stopped being true and gives the pending queue a natural size. A lapsing window is not a decision anyone made, so it is derived rather than stored — pending, deadline present, deadline passed — and the Order status set is unchanged: Pending, Verified, and Rejected remain the three outcomes of a decision, and a lapsing window is not one of them. Nothing sweeps, expires, or deletes a lapsed Order; it is replaced by a new one at the current price. That is why the flag can be derived: there is no job to fall behind.

A resubmission does not extend the window. Resubmission amends the same Order, so a window that extended on each attempt could be held open indefinitely by resubmitting, which would defeat the window entirely. A fresh window per attempt is a different design and would have to be said out loud; this is the reading that matches why the window exists at all.

The deadline is nullable and null means no window, which is how Orders that predate the column stay submittable forever. There is no backfill: backfilling would instantly lapse every pending Order on the instance, including any with a payment already in flight.

One rule covers USDT and LTC alike. The Rate only moves for LTC, but a single rule is simpler, bounds the queue, and avoids doubling the states every surface has to render. The user-facing message for a lapsed window therefore does not blame the Rate, because for a USDT Order nothing moved.

The window bounds when a customer may start paying, not what an Admin may read afterwards. An Order whose payment details arrived inside the window has a real on-chain event behind it and stays verifiable and amendable however long the Admin takes to get to it — the same reasoning that keeps the Rate's staleness bound at quote time only. Refusing a customer who paid the figure they were quoted would be worse than the exposure the bound prevents. The server (`windowClosedForSubmission`) and the Verification queue (`isDead`) implement that one rule separately, deliberately, because each owns a different surface; they are kept in step by tests on both sides.
